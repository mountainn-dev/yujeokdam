# 유적담 (遺跡談) — 설계 문서

- **작성일**: 2026-06-08
- **대상**: 한국관광공사 관광데이터 활용 공모전 (웹/앱 부문)
- **제출물**: 기획서 + 작동하는 앱
- **제약**: 개발 인력 1명, 기간 1~3개월

---

## 1. 개요

### 한 줄 정의

경주 유적지에 얽힌 이야기를 **역사 인물 간 채팅 형식**으로 풀어내어, 유적지 관광을 더 풍부하게 만드는 Flutter 앱.

### 문제와 페르소나

대상 사용자는 역사 배경지식이 많지 않아 유적지를 가도 신비한 분위기와 건물 양식 같은 1차적 인상만 즐긴다. 그러나 역사 영화를 본 뒤에는 관련 유적지가 특별하게 다가오고, 안내문 이해도 잘 된다.

**유적담은 그 "역사 영화"의 역할을 대신한다.** 영화와 동등한 퀄리티를 제공하진 못하지만, 앱의 콘텐츠를 계기로 사용자가 해당 유적지 관련 자료를 찾아보게 만들어, 이전보다 훨씬 풍부한 유적지 관광으로 이어지게 한다.

### 범위

- **지역**: 경주 특화. 경주 내 유적지만 다룬다.
- **콘텐츠 제작**: LLM으로 초안 생성 → 사람이 직접 감수 → 정적 데이터로 탑재.
- **관광데이터 활용**: 이야기 완독 후 '이야기의 무대' 화면에서 TourAPI를 실시간 활용.
- **백엔드 없음**: 콘텐츠는 앱 내장, TourAPI는 앱에서 직접 호출.

### 보류 / 향후 로드맵 (이번 범위 아님)

- **역사 인물 기반 AI 채팅 봇**: 이야기 완독 후 인물과 추가 대화. 구현 복잡도와 역사 왜곡 리스크로 2단계 로드맵으로 명시.
- **원격 콘텐츠 관리(CMS) / 백엔드 전환**: 콘텐츠가 수백 개로 커지면 Firebase/Supabase 등으로 전환. 데이터 모델을 repository 패턴으로 설계해두어 구현체 교체 수준으로 이전 가능.

## 2. 화면 구조와 핵심 플로우

### 핵심 플로우

```
이야기 발견 → 채팅 뷰어로 읽기 (탭 진행) → 완독 → '이야기의 무대' → (방문 동기 형성)
                     │
                     └─ 인물 아바타 탭 → 인물 프로필 → 관련 이야기로 이동
```

### 화면 목록 (5개)

**① 홈 — 이야기 목록**
메신저 앱의 '대화방 목록' 메타포. 각 이야기가 채팅방처럼 보인다 — 인물 아바타 묶음, 이야기 제목, **NEW 배지**(아직 안 읽은 이야기). 마지막 대사 미리보기는 두지 않는다. 상단에 유적지별/테마별 필터 칩. "앱을 여는 순간부터 채팅 앱 같다"는 인상이 컨셉을 즉시 전달한다.

**② 채팅 뷰어 — 이야기 읽기**
화면 아무 데나 탭하면 다음 말풍선이 나타난다. 인물별 아바타·이름·말풍선 색 구분, 중간중간 시스템 메시지(나레이션)로 장면 전환. 말풍선의 인물 아바타를 탭하면 ④ 인물 프로필로 이동. 완독 시 자연스럽게 ③으로 이어진다.

**③ 이야기의 무대 — TourAPI 연동**
이야기가 끝나면 "이 이야기의 무대를 만나보세요" 화면. TourAPI에서 해당 유적지의 대표사진·주소·운영시간·요금 + 유네스코 세계유산 배지(해당 시) + 사진 갤러리 + 주변 관광지/음식점 목록. 공모전 평가 기준인 '관광데이터 활용'이 가장 선명하게 드러나는 화면으로, 데모 시나리오의 클라이맥스에 배치한다. 하단에 이야기 출처 표기.

**④ 인물 프로필**
초상, 생몰년, 한 줄 소개, 짧은 설명, **관계도**(연결된 인물을 선으로 잇고 "라이벌"·"군신"·"부부" 등 관계 라벨 표시), 등장 이야기 목록. 관계도의 인물을 탭하면 그 인물 프로필로 점프 — 탐색의 두 번째 경로.

**⑤ 인물 도감 (탭)**
전체 등장인물 그리드. 아직 안 읽은 이야기의 인물은 실루엣 처리해 가벼운 수집 욕구를 유도(별도 스탬프 기능 없이 수집감 제공).

### 내비게이션

하단 탭 2개: **이야기(홈) · 인물**. 설정은 홈 우상단 아이콘. (지도 탭은 이번 범위에서 제외.)

## 3. 데이터 모델과 TourAPI 연동

> 아래 JSON은 **어떤 데이터가 존재하고 무엇과 연결되는지**를 설명하는 개념 스케치다. 실제 구현 클래스 구조는 구현 단계에서 프로젝트 계층 컨벤션(data/domain/view 스킬)을 따른다.

### 콘텐츠 데이터 (앱 내장 JSON 에셋)

**Story (이야기)**
```json
{
  "id": "story_001",
  "title": "서출지, 까마귀가 전한 편지",
  "siteId": "site_seochulji",
  "characterIds": ["soji_king", "court_lady"],
  "tags": ["신라", "설화"],
  "sources": ["삼국유사 권1 기이편"],
  "messages": [
    { "type": "narration", "text": "신라 소지왕 10년, 정월 보름..." },
    { "type": "chat", "characterId": "soji_king", "text": "..." }
  ]
}
```

**Character (인물)**
```json
{
  "id": "soji_king",
  "name": "소지왕",
  "portrait": "assets/portraits/soji_king.png",
  "lifespan": "?~500",
  "oneLiner": "신라 21대 왕",
  "description": "...",
  "relations": [ { "targetId": "court_lady", "label": "군신" } ]
}
```

**HeritageSite (유적지)**
```json
{
  "id": "site_seochulji",
  "name": "서출지",
  "tourApiContentId": "126312",
  "tourApiContentTypeId": "12"
}
```

유적지의 사진·주소·운영시간 같은 정보는 JSON에 넣지 않고 `tourApiContentId`만 들고 있다가 TourAPI에서 실시간으로 가져온다. 데이터 중복을 없애고, "관광공사 데이터를 살아있는 상태로 쓴다"는 점을 명확히 한다.

### 저장소 선택 근거

| 데이터 | 성격 | 저장소 |
|---|---|---|
| 이야기·인물·유적지 | 읽기 전용 원본, 소량, 빌드 동봉 | **assets (JSON)** |
| 열어본 이야기 id, TourAPI 응답 캐시 | 사용자측 가변·소량 | **shared_preferences** |

콘텐츠를 sqflite가 아닌 assets로 두는 이유: (1) 읽기 전용 + 빌드 동봉이라 별도 seeding/마이그레이션이 불필요, (2) 데이터가 작아 메모리에 통째로 올려 필터링하면 충분, (3) 쿼리 패턴이 단순해 JOIN·인덱싱 불필요, (4) "JSON 수정 → 빌드" 감수 워크플로우와 직결되어 소스 이중화가 없다. 콘텐츠가 수백 개로 커지면 그때 sqflite/원격 DB로 전환한다(향후 확장).

**NEW 배지**: shared_preferences에 '열어본 이야기 id 집합'을 기록, 목록에서 그 집합에 없는 이야기에 NEW 표시. 별도 버전 관리 없이 신규 콘텐츠에도 자동 대응(새 id는 자연히 집합에 없음).

### TourAPI 연동 ('이야기의 무대' 화면)

- **서비스**: KorService2 (국문 관광정보, v4.4)
- **Base URL**: `https://apis.data.go.kr/B551011/KorService2/` (HTTPS 사용)
- **응답 형식**: `&_type=json`
- **필수 공통 파라미터**: `serviceKey`, `MobileOS`(AND/IOS), `MobileApp`(유적담)

| 화면 용도 | 오퍼레이션 | 필수 파라미터 |
|---|---|---|
| 개요·주소·대표사진·홈페이지 | `detailCommon2` | `contentId` |
| 운영시간·휴무·요금·유네스코 유산 여부 | `detailIntro2` | `contentId`, `contentTypeId` |
| 사진 갤러리 | `detailImage2` | `contentId` |
| 주변 관광지/음식점 | `locationBasedList2` | `mapX`, `mapY`, `radius`(필수), `contentTypeId` 필터, `arrange=E`(거리순) |

- **유네스코 배지**: `detailIntro2`(관광지 타입 12)의 `heritage1/2/3` 필드(세계문화/자연/기록유산 유무)로 불국사·석굴암 등에 "유네스코 세계유산" 배지 자동 표시.
- **호출량 제약**: 개발계정은 **일 1,000건**. 무대 화면 1회 열람당 최대 4콜 → 캐시가 필수(아래 에러 처리 참조). 정식 운영 시 운영계정 전환.

## 4. 기술 스택 · 에러 처리

### 기술 스택 (Flutter, 백엔드 없음)

- **상태관리/DI**: GetIt + Provider (프로젝트 view-layer 컨벤션과 일치)
- **네트워크**: `http` 패키지 (TourAPI 호출만 하므로 충분)
- **로컬 저장**: `shared_preferences` (NEW 배지용 열람 기록, TourAPI 응답 캐시)
- **콘텐츠**: `assets/`에 JSON 번들 (stories / characters / sites) + 인물 초상 이미지
- **지도**: 지도 탭 제외. 무대 화면의 위치는 정적 지도 이미지 또는 좌표 텍스트 + "지도 앱으로 열기" 링크로 대체 → 지도 SDK 의존성 0

> 구현은 프로젝트 계층 컨벤션(data / domain / view 스킬: DTO·mapper·repository_impl, `Result<T>`/`ServiceError`, `BaseRepository.execute`, DI 모듈, StateHolder/ViewModel 분리)을 따른다.

### 에러 처리 (계층별)

- **콘텐츠 레이어**: 앱 내장 JSON이라 실패 불가. 앱 시작 시 1회 파싱 → 메모리 보관. 이야기 읽기는 100% 오프라인 동작 보장.
- **TourAPI 레이어**: 무대 화면만 네트워크 의존.
  - 성공 응답을 `contentId`별로 로컬 캐시 → 재방문 시 캐시 우선, 일 1,000콜 절약 + 심사 시연 안전장치.
  - 실패 시: 캐시 있으면 캐시 표시 / 없으면 "유적지 이름 + 재시도 버튼" 빈 상태 화면.
  - `resultCode != "0000"`(API 에러코드)도 네트워크 실패와 동일 처리.
  - repository 반환은 `Result<T>` / `ServiceError`로 통일 (domain-layer 컨벤션).

## 5. 콘텐츠 제작 워크플로우

기획서에서 "어떻게 양질의 콘텐츠를 확보하는가"가 평가 포인트이므로 명문화한다.

```
1. 유적지 선정 → searchKeyword2로 tourApiContentId 확보 (1회성)
2. 사료 수집 (정사·설화 출처 기록)
3. LLM으로 채팅 대본 초안 생성 (인물·말풍선 구조)
4. 사람 감수: 사실 검증, 어디까지 사료 / 어디부터 각색인지 구분
5. JSON 작성 → 에셋 반영 → 빌드
```

- **신뢰성 장치**: 각 Story에 `sources`(출처) 필드를 두고, 무대 화면 하단에 출처 표기. 역사 왜곡 논란 방어 + 교육적 신뢰도.
- **데모용 최소 분량**: 경주 유적지 5~8곳 × 이야기 1개씩이면 심사 시연에 충분. 완성도 우선.

## 6. 평가 기준 정합성 (공모전 관점)

- **관광데이터 활용**: '이야기의 무대' 화면에서 TourAPI 4개 오퍼레이션을 실시간 활용 — 단순 목록 노출이 아니라 "이야기 → 실제 방문"으로 데이터를 연결.
- **차별성**: 채팅 형식 스토리텔링 + 인물 관계도 탐색은 기존 관광 정보 앱에 없는 접근.
- **완성도**: 백엔드 없는 정적 구조 + 오프라인 동작 보장으로 심사 시연 안정성 확보.
- **확장성**: AI 채팅 봇, CMS/백엔드 전환을 로드맵으로 제시해 비전 전달.
