# 서브에이전트 평가 및 테스트

<evaluation_framework>


<task_completion>
**1차 지표**: 올바르고 만족스럽게 완료된 작업의 비율.

측정 항목:
- 서브에이전트가 요청된 작업을 완료했는가?
- 예상 출력을 생성했는가?
- 사람이 작업을 "완료"로 간주하는가?

**테스트 접근 방식**: 알려진 예상 결과를 가진 테스트 케이스를 만들고, 서브에이전트를 호출하여 결과를 비교한다.
</task_completion>

<tool_correctness>
**2차 지표**: 서브에이전트가 주어진 작업에 올바른 도구를 호출하는지 여부.

측정 항목:
- 도구 선택이 작업에 적합한가?
- 도구를 효율적으로 사용하는가 (불필요한 도구를 호출하지 않는가)?
- 올바른 순서로 도구를 사용하는가?

**테스트 접근 방식**: 실행 로그에서 도구 호출 패턴을 검토한다.
</tool_correctness>

<output_quality>
**품질 지표**: 서브에이전트가 생성한 출력의 품질을 평가한다.

측정 항목:
- 분석의 정확성
- 커버리지의 완전성
- 커뮤니케이션의 명확성
- 지정된 형식 준수

**테스트 접근 방식**: 사람의 검토 또는 LLM-as-judge 평가.
</output_quality>

<robustness>
**견고성 지표**: 서브에이전트가 실패와 엣지 케이스를 얼마나 잘 처리하는지.

측정 항목:
- 누락된 파일의 우아한 처리
- 도구 실패로부터의 복구
- 예상치 못한 입력에 대한 적절한 응답
- 경계 조건 처리

**테스트 접근 방식**: 실패를 주입하고 (누락된 파일, 잘못된 형식의 데이터) 응답을 확인한다.
</robustness>

<efficiency>
**성능 지표**: 응답 시간과 리소스 사용량.

측정 항목:
- 토큰 사용량 (비용)
- 지연 시간 (응답 시간)
- 도구 호출 수

**테스트 접근 방식**: 여러 호출에 걸쳐 지표를 모니터링하고 추세를 추적한다.
</efficiency>
</evaluation_framework>

<g_eval>


**G-Eval**: 자연어로 정의된 임의의 맞춤 기준에 따라 출력을 평가하기 위해 chain-of-thought를 가진 LLM을 사용한다.

<example>
**맞춤 기준**: "보안 검토 완전성"

```markdown
보안 검토 출력을 1~5점 척도로 평가하라:

1. 중요한 취약점 유형 누락
2. 기본적인 취약점은 다루지만 일부 일반적인 패턴 누락
3. 표준 OWASP Top 10 취약점 다룸
4. 프레임워크별 문제를 포함한 포괄적인 커버리지
5. 비즈니스 로직 취약점을 포함한 탁월한 커버리지

어떤 취약점이 확인되었고 어떤 것이 누락되었는지 단계적으로 생각하라.
```

**구현**: 서브에이전트 출력과 기준을 Claude에 전달하고, 구조화된 평가를 받는다.
</example>

**사용 시점**: 프로그래밍 방식으로 측정할 수 없는 복잡한 품질 지표 (철저함, 통찰력 품질, 권고사항의 적절성).
</g_eval>

<validation_strategies>


<offline_testing>
**오프라인 검증**: 합성 시나리오로 배포 전 테스트.

**프로세스**:
1. 다음을 포괄하는 대표적인 테스트 케이스 생성:
   - 정상 경로 시나리오
   - 엣지 케이스 (경계 조건, 비정상적인 입력)
   - 오류 조건 (누락된 데이터, 도구 실패)
   - 적대적 입력 (잘못된 형식, 악의적인)
2. 각 테스트 케이스로 서브에이전트 호출
3. 출력을 예상 결과와 비교
4. 실패를 문서화하고 프롬프트를 반복 개선

**`code-reviewer` 서브에이전트를 위한 테스트 스위트 예시**:
```markdown
테스트 1 (정상 경로): SQL 인젝션 취약점이 있는 최근 커밋
예상: SQL 인젝션 식별, 수정 제공, 심각으로 평가

테스트 2 (엣지 케이스): 최근 코드 변경 없음
예상: 검토 완료 확인, 문제 없음

테스트 3 (오류 조건): Git 저장소 초기화되지 않음
예상: 누락된 git을 우아하게 처리, 유용한 메시지 제공

테스트 4 (적대적): 숨겨진 취약점이 있는 난독화된 코드
예상: 난독화에도 불구하고 패턴 식별
```
</offline_testing>

<simulation>
**시뮬레이션 테스트**: 현실적이지만 통제된 환경에서 서브에이전트 실행.

**사용 사례**:
- 역사적 문제에 대한 테스트 (이전에 수정된 버그를 찾을 수 있는가?)
- 벤치마크 데이터셋 (코드 에이전트용 SWE-bench)
- 알려진 취약점이 있는 통제된 코드베이스

**장점**: 합성 테스트보다 높은 신뢰도, 프로덕션 테스트보다 안전.
</simulation>

<online_monitoring>
**프로덕션 모니터링**: 실제 사용 중 지표 추적.

**핵심 지표**:
- 성공률 (완료 vs 실패 작업)
- 사용자 만족도 (명시적 피드백)
- 재시도율 (실패 후 사용자가 재호출하는 빈도)
- 토큰 사용량 추세 (증가 = 잠재적 프롬프트 문제)
- 오류 유형별 오류율

**구현**: 컨텍스트, 결과, 지표를 포함한 모든 호출을 로깅하라. 패턴을 위해 정기적으로 검토하라.
</online_monitoring>
</validation_strategies>

<evaluation_driven_development>


**철학**: 검증 단계에서만이 아니라 서브에이전트 수명주기 전반에 걸쳐 평가를 통합한다.

<workflow>
1. **초기 생성**: 프롬프트 작성 전 성공 기준 정의
2. **개발**: 각 프롬프트 반복 후 테스트
3. **배포 전**: 포괄적인 오프라인 테스트
4. **배포**: 지표 수집을 통한 온라인 모니터링
5. **반복**: 실패에 대한 정기적 검토, 학습을 기반으로 프롬프트 업데이트
6. **지속**: 지속적인 평가 → 피드백 → 개선 사이클
</workflow>

**안티패턴**: 서브에이전트를 작성하고 배포한 후, 효과성을 측정하거나 반복 개선하지 않는 것.

**모범 사례**: 서브에이전트 프롬프트를 실제 성능 데이터를 기반으로 발전하는 살아있는 문서로 취급하라.
</evaluation_driven_development>

<testing_checklist>


<before_deployment>
서브에이전트를 배포하기 전에 다음 검증을 완료하라:

**기본 기능**:
- [ ] 대표적인 작업으로 호출하여 완료 확인
- [ ] 출력 형식이 명세와 일치하는지 확인
- [ ] 워크플로 단계가 순서대로 따라지는지 확인
- [ ] 제약이 준수되는지 확인

**엣지 케이스**:
- [ ] 누락되거나 불완전한 데이터로 테스트
- [ ] 비정상적이지만 유효한 입력으로 테스트
- [ ] 경계 조건으로 테스트 (빈 파일, 대용량 파일 등)

**오류 처리**:
- [ ] 사용 불가능한 도구로 테스트 (도구 접근이 제한된 경우)
- [ ] 잘못된 형식의 입력으로 테스트
- [ ] 이상적인 경로 실패 시 우아한 저하 확인

**품질 확인**:
- [ ] 정확성을 위한 출력의 사람 검토
- [ ] 환각이나 조작된 정보 없음 확인
- [ ] 출력이 실행 가능하고 유용한지 확인

**보안**:
- [ ] 도구 접근이 최소 권한 원칙을 따르는지 확인
- [ ] 잠재적으로 안전하지 않은 작업 확인
- [ ] 민감한 데이터 처리가 적절한지 확인

**문서화**:
- [ ] `description` 필드가 사용 시점을 명확히 나타내는지 확인
- [ ] 역할과 집중 영역이 구체적인지 확인
- [ ] 워크플로가 완전하고 논리적인지 확인
</before_deployment>
</testing_checklist>

<synthetic_data>


<when_to_use>
합성 데이터 생성이 유용한 경우:
- **콜드 스타트**: 아직 실제 사용 데이터가 없을 때
- **엣지 케이스**: 실제 데이터에서 포착하기 어려운 드문 시나리오
- **적대적 테스트**: 보안, 견고성 테스트
- **시나리오 커버리지**: 입력 공간의 체계적인 커버리지
</when_to_use>

<generation_approaches>
**페르소나 기반 생성**: 다양한 사용자 페르소나에서 테스트 케이스 생성.

```markdown
페르소나: 주니어 개발자
작업: "로그인 페이지가 충돌하는 버그를 수정해주세요"
예상 동작: 서브에이전트가 상세한 디버깅 단계 제공

페르소나: 시니어 엔지니어
작업: "인증 흐름 보안을 조사해주세요"
예상 동작: 서브에이전트가 심층 보안 분석 수행
```

**시나리오 시뮬레이션**: 일반적인 시나리오의 변형 생성.

```markdown
시나리오: SQL 인젝션 취약점 검토
변형:
- 직접 SQL 연결
- 원시 쿼리를 사용하는 ORM
- Prepared statements (통과해야 함)
- 동적 SQL을 가진 저장 프로시저
```
</generation_approaches>

<critical_limitation>
**합성 데이터에만 의존하지 마라.**

실제 사용 예시의 검증 세트를 유지하라. 합성 데이터는 다음을 놓칠 수 있다:
- 실제 세계의 복잡성
- 실제 사용자 의도 패턴
- 프로덕션 환경 제약
- 창발적 사용 패턴

**모범 사례**: 70% 합성 (커버리지용), 30% 실제 (현실 확인용).
</critical_limitation>
</synthetic_data>

<llm_as_judge>


<basic_pattern>
규모에서 사람의 검토가 어려울 때 LLM을 사용하여 서브에이전트 출력을 평가한다.

**평가 프롬프트 예시**:
```markdown
AI 서브에이전트가 수행한 보안 코드 검토를 평가하는 중입니다.

검토 출력:
{subagent_output}

검토된 코드:
{code}

다음 기준으로 평가하라:
1. 정확성: 식별된 취약점이 실재하는가? (예/부분/아니오)
2. 완전성: 명백한 취약점이 누락되었는가? (누락 없음/일부 누락/다수 누락)
3. 실행 가능성: 수정이 구체적이고 구현 가능한가? (매우/다소/별로)

다음을 제공하라:
- 전체 등급 (A/B/C/D/F)
- 검토의 특정 문제점
- 사람 검토자가 다르게 했을 점
```
</basic_pattern>

<comparison_pattern>
**정답 비교**: 올바른 답이 알려진 경우.

```markdown
테스트 코드의 예상 취약점:
1. 42번 줄의 SQL 인젝션
2. 67번 줄의 XSS 취약점
3. 103번 줄의 누락된 인증 확인

서브에이전트가 식별한 것:
{subagent_findings}

계산:
- 정밀도: 식별된 문제 중 실제인 비율
- 재현율: 실제 문제 중 식별된 비율
- F1 점수: 정밀도와 재현율의 조화 평균
```
</comparison_pattern>
</llm_as_judge>

<test_driven_development>


Anthropic 지침: "테스트 주도 개발은 에이전트 코딩에서 더욱 강력해진다."

<approach>
**서브에이전트 프롬프트 작성 전**:
1. 예상 입력/출력 쌍 정의
2. 서브에이전트가 통과해야 할 테스트 케이스 생성
3. 초기 프롬프트 작성
4. 테스트 실행, 실패 관찰
5. 실패를 기반으로 프롬프트 개선
6. 모든 테스트가 통과할 때까지 반복

**`test-writer` 서브에이전트를 위한 예시**:
```markdown
테스트 1:
입력: 두 수를 더하는 함수
예상 출력: 다음을 포함한 테스트 파일:
  - 정상 경로 (2 + 2 = 4)
  - 엣지 케이스 (0 + 0, 음수)
  - 타입 오류 (문자열 + 숫자)

테스트 2:
입력: 사용자 데이터를 가져오는 비동기 함수
예상 출력: 다음을 포함한 테스트 파일:
  - 성공적인 가져오기
  - 네트워크 오류 처리
  - 잘못된 사용자 ID 처리
  - Mock HTTP 호출 (실제 API 호출 없음)
```

**서브에이전트 호출 → 출력이 예상과 일치하는지 확인 → 프롬프트 반복 개선.**
</approach>

**장점**: 개발 전 명확한 인수 기준, 프롬프트 품질의 객관적 측정.
</test_driven_development>

<anti_patterns>


<anti_pattern name="no_testing">
❌ 검증 없이 서브에이전트 배포

**위험**: 서브에이전트가 실제 작업에서 실패하고, 사용자 시간을 낭비하며, 신뢰를 손상시킨다.

**수정**: 최소 검증 = 배포 전 3개의 대표적인 작업으로 호출.
</anti_pattern>

<anti_pattern name="only_happy_path">
❌ 이상적인 시나리오만 테스트

**위험**: 서브에이전트가 엣지 케이스, 오류 조건, 또는 비정상적이지만 유효한 입력에서 실패한다.

**수정**: 정상 경로, 엣지 케이스, 오류 조건을 포괄하는 테스트 매트릭스.
</anti_pattern>

<anti_pattern name="no_metrics">
❌ 효과성 측정 없음

**위험**: 프롬프트 변경이 성능을 향상시키는지 저하시키는지 알 수 없다.

**수정**: 최소 하나의 정량적 지표 정의 (작업 완료율, 출력 품질 점수).
</anti_pattern>

<anti_pattern name="test_once_deploy_forever">
